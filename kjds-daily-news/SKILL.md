# 跨境电商每日早报 Skill

## Purpose

从指定一手渠道采集全球跨境电商最新动态，精选对亚马逊卖家有实际参考价值的内容，生成符合玻璃拟态设计风格的HTML早报文件。

**核心原则**：宁可收录7条精确链接的新闻，也不要收录14条但一半链接有问题。数量不是目标，可信度才是。

## When to Use

- 用户说"生成跨境早报"、"今天有什么跨境资讯"、"每日早报"
- 自动化任务每日定时触发（默认早上8:30）
- 用户需要了解最新跨境电商政策、平台动态、合规变动

---

## 规则分类

为避免硬性规则、质量目标和展示偏好互相干扰，以下将规则分为三个明确类别。

### A. 硬性约束（必须遵守，无例外）

1. 链接可访问（非404/500/520）
2. 链接为**具体文章页**（非列表页/聚合页/搜索页）
3. 来源标签与链接域名一致
4. 摘要内容、日期和链接正文相符
5. 不使用 T3 禁用来源
6. 不编造事实 — 所有摘要必须基于实际抓取的内容
7. 所有最终链接均完成四维验证
8. 淘汰记录必须有具体根因（不允许"其他原因"）
9. **最终链接域名必须已在总表登记**（T0/T1；社区观察例外仅限 wearesellers.com / reddit.com）。发现表外高价值候选时，必须先实测其域名并登记入总表（附定级理由）再使用，**禁止先斩后奏**——validator 第 3 项检查会拦截一切未登记域名（代码: SOURCE_NOT_IN_REGISTRY）

### B. 质量目标（尽力达成，允许弹性）

1. 版面基准 13 条（①3 ②3 ③2 ④2 ⑤3），**各区上限 ①6 ②4 ③4 ④4 ⑤3**，正常范围 **13–21** 条，P0 不限分区配额但受全局 40% 上限约束；低新闻量日按实际数量出，不足 7 条在审计说明原因
2. **① 平台政策与费用区：Amazon / Walmart / TikTok Shop 三个平台各至少 1 条，该区最多 6 条**（详见 5.5）
2. 尽量增加来源多样性
3. 同一来源通常不超过 2 条，重大连续公告可例外
4. 优先选择对卖家有明确行动价值的内容
5. 优先使用能直接抓取到原文内容的渠道
6. 条目不足时允许少报，不允许降低验证标准

### C. 展示偏好（灵活处理）

1. 玻璃拟态设计风格（Glass Morphism）
2. 桌面端按固定主题分区列表展示，移动端单列
3. 卡片颜色由所属主题分区固定，不循环覆盖
4. 英文章节标题采用"中文翻译 (English Original Title)"格式
5. 卡片 meta 标签顺序：date → source → [optional badge]

## 来源分级体系

来源分级与采集频率的唯一权威定义见本 skill 的 `references/跨境资讯一手信息源总表.md`，随 skill 自包含分发，不依赖任何外部项目目录。

| 等级 | 定义 | 判定依据 | 能否作为最终链接 |
|:----:|------|---------|:--------------:|
| 🟢 **T0** | 政府、监管机构、平台或企业的官方公告/官方数据 | 按**内容发布主体**判定 | ✅ 可以 |
| 🔵 **T1** | 有编辑责任的原创行业媒体、独立调查/研究/分析 | 按**内容性质**（原创而非转载）判定 | ✅ 可以 |
| 🟡 **T2** | 社区讨论、自媒体、社交媒体、转载文章及未经确认的线索 | 按**有无编辑审核机制**判定 | ❌ 原则上不可 |
| 🔴 **T3** | 聚合、采集、洗稿、搜索结果及其他非原文页面 | 按**是否原文发布**判定 | ❌ 严禁 |

### 按内容类型的最终链接裁决表

这是解决"必须一手源"与"允许转载补位"规则冲突的唯一权威判定依据：

| 内容类型 | 最终链接要求 |
|---------|-------------|
| 官方政策、平台规则、监管公告 | 必须使用对应 🟢 T0 原文 |
| 行业研究、数据报告、媒体调查 | 可以使用该研究或调查的 🔵 T1 原创页面 |
| 转载或翻译文章 | 只能作为发现线索，找到原文后替换；找不到则淘汰 |
| 社区讨论（知无不言/Reddit） | 仅当"社区反应或卖家讨论本身"是报道对象时可引用，并明确标注为社区观察 |
| 社交媒体消息 | 一律仅作线索，不作最终链接；报道对象须追溯到 T0/T1 原文 |

### 红线规则

- **任何来源标签的域名必须与链接域名一致**。不允许出现"来源标A，链接指B"。
- **任何最终链接的域名必须已在总表登记**（T0/T1 + 社区观察例外域）。表外高价值源先登记（实测域名+定级理由）再引用。
- 引用 AMZ123、卖家之家等聚合站的内容时，必须标注原始出处（如「亚马逊全球开店」），而非聚合站本身。
- **大数跨境（10100.com）与出海网（chwang.com）已于 2026-10-20 升为 T3 禁用**（聚合/UGC 平台，非一手也非原创编辑媒体）：不采集、不作线索、不作来源，其域名出现在任何链接中即被 validator 以 `FORBIDDEN_DOMAIN` 拦截。若信息本身有价值，必须绕过其页面、直接找到原始发布方（T0/T1）再立卡。
- 如果某条资讯只有二手转载，宁可不收录。
- 公众号文章当前不可作最终链接（总表无公众号源，白名单不含 `mp.weixin.qq.com`）。将来若重新登记，来源等级须按**账号主体**判定，不只看域名。

### 引用标注格式（写进卡片的 `card-source`）

| 等级 | 标注方式 |
|:----:|---------|
| 🟢 T0 | 直接标「来源」 |
| 🔵 T1 | 标「来源（行业分析）」 |
| 🟡 T2 | 默认仅作线索；报道对象是社区反应/卖家讨论本身时，标「社区观察」，不得把未证实主张写成事实 |
| 🔴 T3 | 严禁标注为来源 |

### 覆盖统计口径（Header 独立来源数）

- **active** = 本期最终卡片中至少有一条来自该渠道
- **checked-no-update** = 检查过但无有效新内容，不计入来源数
- **发现型渠道（role=discovery / T2 线索）不计入独立来源数**；仅作为社区观察最终链接的 T2 来源，按卡片实际主体计入

### 登录墙与替代口径

- **Seller Central 已从总表移除**（路径 404 + 登录墙）：其职责由 `gs.amazon.cn`（中文日更）与 `sell.amazon.com/blog/announcements`（英文月更）承担。EcomCrew 等 T1 页面只能帮助**发现**公告，最终卡片仍须回到可核验的官方原文；取不到官方原文则淘汰，不得用 T1 页面冒充 T0。
- **TikTok Shop 卖家中心**：`seller-us.tiktok.com/university/essay?...` 是 SSR 可读（须带浏览器 UA），不算登录墙，见总表行 19。

## 运行上下文（每次执行开始时初始化）

```yaml
run_date: 当前日期（Asia/Shanghai）
lookback_days: 2
weekend_lookback_days: 3          # 周一允许回溯到上周五/六/日
current_year: 从 run_date 计算
current_month_en: 从 run_date 计算（如 "July"）
current_month_num: 从 run_date 计算（如 "7"）
current_month_zh: 从 run_date 计算（如 "7月"）
date_from: run_date - lookback_days
date_to: run_date
# 窗口是采集与排序依据，不是淘汰门槛：窗口外候选若首发日可确认且属今日新发现，可收录，卡片标注实际首发日并在审计注明；已验证的官方 deadline/活动提醒例外保留
search_suffix: "current_month_en current_year"  # 通用搜索词后缀
# 跨日去重上下文（见步骤3.1 零成本硬淘汰）
dedup_window: 2                    # 读取前 N 天报告做去重（周一=3，其他=2，与周末回溯对齐）
prior_reports:                     # 查找顺序：先根目录，未命中再查 归档/YYYY-MM/（历史报告按月归档）
  - 跨境早报-{run_date-1}.html     # run_date 前 1 天，如 跨境早报-2026-07-16.html（或 归档/2026-07/跨境早报-2026-07-16.html）
  - 跨境早报-{run_date-2}.html     # run_date 前 2 天（若存在）
# 长窗口话题记忆（见步骤2.3 预筛 / 步骤3.1 去重 / 步骤6.4 回写）
project_state_dir: 早报状态/     # 项目运行状态；新项目初始化为空，不从 skill 包历史自动导入
shortlist_target: 38              # ②③④⑤ 按各自上限 ×2；① 例外取 8（非 12）：三平台各 2-3 条候选足够覆盖「各至少 1 条」
early_stop_candidates: 38         # 早停总量阈值（= shortlist_target）
                                  # 必须 ≥ shortlist_target：低于它早停会导致验证后填不满版面
early_stop_zone_min:              # 分区覆盖下限（早停双条件之二）
  cat-policy: 3                   # ① 平台政策与费用
  cat-reg: 3                     # ② 合规与监管
  cat-logistics: 4               # ③ 物流与供应链
  cat-market: 2                  # ④ 行业与市场
  cat-community: 3               # ⑤ 卖家社区
                                  # 合计 15，按 Tier A 各区源数定（①3 ②3 ③4 ④2 ⑤1，⑤ 虽单源但目标产 3 条）
                                  # ⚠️ 下限只能 ≤ Tier A 在该区的源数，否则条件可满足性为零：
                                  #    v2.10.14 之前是 ①5②5③4④4⑤5=23，而 ⑤ 区 Tier A 只有知无不言 1 个源、
                                  #    目标 3 条，永远到不了 5 → 早停永不触发，每期白跑 Tier B
                                  # 它与 shortlist 配额（38）是两层：这个只保证「每区有货」，
                                  # 不足的区在 3.3 按「缺口让给候选最多的区」处理
```

`references/channel-health.md` 是**空表模板**（无渠道数据），禁止作为新项目的运行状态自动加载。首次在项目运行时创建 `早报状态/topic-registry.md` 与 `早报状态/channel-health.md`（按空表/模板）；已有项目只有在明确授权时，才按来源和话题指纹逐项迁移，保留来源证据、跳过未匹配项，不覆盖项目现有记录。预筛只能使用已验证的项目级状态。

所有实际搜索词使用上述动态变量；文中的历史日期和格式示例不能作为本次运行日期。

## 工作流

### 步骤 1：初始化运行上下文

**输入**：无（自动读取系统时间）
**输出**：运行上下文（run_date / 时区 / 回溯窗口 / 启用渠道 / 输出路径）

1. 读取当前日期和时间（Asia/Shanghai）
2. 根据星期几决定回溯天数（周一=3天，其他=2天）
3. **滚动归档（主动执行，不依赖"下次运行顺便做"）**：把当前工作目录根目录中、除最近 2 天外的所有 `跨境早报-YYYY-MM-DD.html` 移入 `归档/YYYY-MM/`（目录不存在则创建）。这样即使隔多日才运行一次，也能一次归拢到位，防止根目录无限堆积
4. 从本 skill 的 `references/跨境资讯一手信息源总表.md` 加载权威来源清单（分级/频率/自动化），执行规则见本文 2.1–2.5
5. 读取项目级 `早报状态/topic-registry.md`（不存在则按空表初始化；skill 包内不携带副本，唯一权威就是项目表）
6. 确定当天输出路径：`跨境早报-YYYY-MM-DD.html`
7. 输出运行上下文到审计记录

### 步骤 2：采集（按分区覆盖早停）

**输入**：运行上下文
**输出**：候选池（去重后，含 `discovered_via` / `source_name` 分离字段）

#### 2.1 采集顺序与分区归属

源清单、分级、频率，以及**每个源主要供给哪个分区**，全部在 `references/跨境资讯一手信息源总表.md` 的「分区」列。本文件**不再复制源名列表**——v2.10.5 之前这里维护过一份副本，加源要改两处，实际发生过「Tier B 采集清单漏 Amazon Ads Blog（19 项 vs 总表 20 项）」的漂移。

采集按 Tier 顺序：**A（每日必查）→ B（每日低优先）→ C（每周，仅线索不计来源数）→ D（条件触发）**。

早停按分区判断，所以要清楚每条候选归哪个区：总表分区列标 `①`–`⑤` 的直接对应；标 `按内容` 的按其实际报道主体判断，口径见 5.6。

> ⚠️ **Maersk 必须留在 Tier A**：③ 区 Tier A 只剩它一家（CMA CGM 已移除），降回 Tier B 会让「③区 ≥4」结构性不成立、早停永不触发。
> ⚠️ **沃尔玛与 TikTok Shop 的官方域只剩 2 个**（亚马逊侧另有 `gs.amazon.cn` / `Amazon Ads` / `seller-us.tiktok.com`）：`marketplacelearn.walmart.com`（Tier A，每日可用）；`seller-us.tiktok.com`（Tier B，essay 页 SSR，须先有 knowledge_id）。**沃尔玛政策供给基本压在这一个源上**，别退回中文媒体转述。
> ⚠️ **③ 区 Tier A 只剩 Maersk 一家**（CMA CGM 已从总表移除）：Container News / FreightWaves / Supply Chain Dive / sea-daily 四个 ③ 区 T1 源要紧接 Tier A 之后查，别排到 Tier B 末尾——否则「③区 ≥4」的早停下限可能凑不满。
> **大数跨境（10100.com）、出海网（chwang.com）为 T3 禁用**：不采集、不作线索。

#### 2.2 早停：两个条件，缺一不可

```
去重后候选数（已剔除标题层可判定的 A1/A2/A3/A6/A8/A9）
  ≥ early_stop_candidates（38）
AND 每区候选数 ≥ early_stop_zone_min（①3 ②3 ③4 ④2 ⑤3，合计 15）
  → 停采，跳过剩余 Tier
```

- **38 = shortlist 目标量（各区上限 × 2：①8 ②8 ③8 ④8 ⑤6）**。阈值低于 shortlist 会导致验证后填不满版面
- **缺区不早停**：宁可多跑一个 Tier 补空区，也不交一份①区空缺的版面
- 知无不言 3 条不是早停硬门槛（早停只看总量与分区下限）；但版面配额里它是 3 条强制目标，见 5.5
- 每个渠道最多 2 次有限重试；仍失败则记录渠道状态并继续。全部 Tier 跑完仍无验证通过候选 → 只交付「今日暂无可验证更新」的审计，不生成 HTML

#### 2.3 采集前置预筛（话题登记表联动）

```
对每条新发现的候选，查 topic-registry.md 活跃话题表（归档区也要扫——归档的是「停止跟踪」，不是「不存在」）：
  命中指纹 且 无新 URL / 新公告 / 新数据 → 不进候选池，直接跳过
  命中 但 有新进展（新公告/新细则/新截止日） → 保留，标「延续报道」
  未命中 → 正常进池
```

> 目的：把去重从「每天采回→验证→淘汰」提前到「源头跳过」。deadline 类话题在窗口内无新公告时每天都会被搜索命中，不预筛就是每天白付一次验证成本。

搜索词用动态变量：
```
"amz123 亚马逊 最新消息 {current_month_zh}{current_year}"
"cpsc recall amazon {current_month_en} {current_year}"
"site:sell.amazon.com/blog {current_year} amazon seller"
```

#### 2.4 候选数据格式

用 `scripts/render-report.py --example` 生成骨架，按其中 `sections.*.cards[]` 的字段填。要点：

- `discovered_via` 与 `source_name` 必须分离。AMZ123、搜索结果、聚合站只能进 `discovered_via`
- 此阶段**不写最终摘要**；`summary` 只记录原文事实，`impact` / `action` 留空到步骤 5 之后再填
- `canonical_url` 在步骤 4 补全，步骤 3 不要填

#### 2.5 公众号采集（当前停用）

> ⚠️ **总表已无公众号源**，`mp.weixin.qq.com` 不在白名单内——任何公众号链接都会被 validator 判 `SOURCE_NOT_IN_REGISTRY`。本节保留备用流程：将来若重新登记公众号源再启用；未登记前**不要引用公众号文章作最终链接**，发现公众号线索也只能用它去溯源 T0/T1 原文。

```
1. jintiankansha.com 或 WebSearch 发现标题与摘要（jintiankansha 只作线索，禁止作最终链接）
2. 用标题搜可选链接，按优先级：
   ① 原始 mp.weixin.qq.com/s/... → 来源标「微信公众号：xxx」
   ② 搜狗微信 redirect（weixin.sogou.com/link?url=...）→ 仅线索，解析后仍须核对账号主体
   ③ T1 转载源（cifnews / jingjiribao 等）→ 仅线索，继续找原文；找不到淘汰
3. 都找不到 → 淘汰
```

> 搜狗索引延迟约 1-2 周。7 天内的新文章优先走 ③ 之外的其他路径。

#### 2.6 特殊源的抓取配方

以下源需要非默认抓取方式。抓不到通常是方式不对，不是没有内容——**先按配方复验，再判「登录墙」或「无内容」**。

**通用兜底顺序（任何源的 HTML 列表页抓不到条目时，按此顺序试完再下结论）**

| 阶 | 通道 | 典型路径 | 适用 |
|:--:|---|---|---|
| 1 | **RSS / Atom** | `/feed`、`/rss`、`/news/feed`、`/feed.xml` | 有 RSS 就一定带 `title` + `link` + `pubDate`，直接可解析。FreightWaves 列表页无 permalink，但 `/news/feed` 一次给 56 条 |
| 2 | **sitemap.xml** | `/sitemap.xml` | 只有 URL + `lastmod`，但路径若内嵌日期（如 Maersk `/news/articles/YYYY/MM/DD/slug`）可直接按日筛；无日期则只能作补位 |
| 3 | **分类页 / 标签页** | `/news/category/xxx`、`/topic/xxx` | 首页是杂志式排版时，分类页常带完整元数据 |
| 4 | WebSearch site: 检索 | `site:域名 {keyword}` | 前三阶都失败时兜底 |

> ⚠️ **教训（2026-10-20）**：FreightWaves 与 Maersk 曾因 HTML 列表页「无 URL / 只有导航」被误判为「结构性不可采」，实际分别有 RSS 和带日期的 sitemap，一条命令就能拿到当日全部条目。**「列表页解析不出条目」不等于「这个源采不到」**，判死之前必须试完 RSS 与 sitemap。

**三平台官方源的 sitemap 配方（2026-10-21 实测）**

| 平台 | 通道 | 实测结构 | 判新增的方法 |
|---|---|---|---|
| **Amazon** | `https://gs.amazon.cn/sitemap.xml` | 3,402 个 URL，**`<lastmod>` 全带**（格式 `YYYY-MM-DD`），其中 `/news/` 类 1,028 条 | `lastmod >= date_from` 直接筛。详情页仍须 WebFetch（curl 裸请求 000） |
| **Walmart** | `https://marketplacelearn.walmart.com/sitemap.xml` | 1,287 个 URL，**无 `lastmod`**；guides 类 1,168 条，路径带完整分类（如 `/guides/Catalog%20management/Item%20management/...`），**均为具体文档页，可直接立卡** | 只能**每日 URL 快照 diff**：上期快照存盘，本期 diff 出新增 URL。发现不了「已有页面被改」，只能发现「新增页」 |
| **TikTok** | `newsroom.tiktok.com/sitemap_index.xml` | 时通时断（10-21 实测超时）；`seller-us.tiktok.com/university/sitemap.xml` 返回 200 但内容是 **CSR 空壳 HTML，假 sitemap** | 无稳定通道。`essay?knowledge_id=` 需种子 ID 才能遍历；搜索引擎几乎不索引官方 essay 页 |

> 🔴 **必须知道的两条事实**（决定「三平台每天各 1 条」能不能做到）：
> 1. **gs.amazon.cn 的 `news` 类 lastmod 最新停在 2026-10-14**，10-15 至 10-21 零新增 —— 是周更偏低频，不是每天发
> 2. **Walmart ML 是静态文档站**（1,287 条长期不变），不是新闻流；`/releasenotes` 无逐条 URL
>
> 结论：**三个平台的官方站都不每天更新**。「每天各 1 条」的瓶颈在平台发布频率，不在采集技术。通道打通只保证「它发了我能发现」，不保证「它每天都发」。

**`sellercentral.amazon.com` 的 Seller Forums 配方（2026-10-21 实测，公开可读）**

Seller News（`/amazonsell/business/container/seller-news`）是登录墙，但**同样的官方公告在 Seller Forums 公开可读**——这是 Amazon 侧的公开替代入口：

| 入口 | 状态 |
|---|---|
| `/seller-forums/discussions` | ✅ 200，511KB，**列表页可直接解析** |
| `/seller-forums/discussions/t/<uuid>` | ✅ 具体帖子页，**可直接立卡** |
| `/news`、`/gp/news` | ❌ 404 |
| `/amazonsell/business/container/seller-news` | ❌ 302 跳 `/ap/signin`（登录墙） |
| `.co.uk/seller-forums/discussions` | ✅ 200，欧洲站同样公开 |

- **官方帖识别**：发帖账号为 Amazon 社区经理（如 `Indy_Amazon`），列表页标 `Pinned by community manager`。正文含具体截止日期、折扣门槛与徽章规则
- **日期陷阱**：列表与帖子页都显示**相对时间**（`a day ago` / `6 days ago`），没有绝对日期。立卡时按抓取日倒推，并在审计注明「相对时间换算」
- **内容陷阱**：官方帖常重提旧政策。如 2026-10-20 的 BFCM 帖里「Amazon Business Deals」实为 9-23 已发布的旧功能；同帖正文写「提交截止 11-13」而 checklist 写「Oct 20」，**帖内自相矛盾**——以卖家后台 Deals Dashboard 为准，不要直接照抄
- **用途定位**：`①区 Amazon 侧的一手补充`。`gs.amazon.cn` 周更、`sell.amazon.com` 月更，Seller Forums 的政策帖是第三条腿

**`seller-us.tiktok.com`（TikTok Shop 美国卖家中心）**
- 目标页：`/university/essay?knowledge_id=...`，SSR 全文可读（实测 19k–23k 字符正文、带 `MM/DD/YYYY` 文章日期、无登录墙）
- 必要条件：**浏览器 UA + HTTP/1.1**，否则连接被重置（返回 000）；本机会话还要 `--noproxy "*"` 绕开注入的死代理
- 发现路径：任一 essay 页 HTML 内嵌 16–22 个 `knowledge_id` 可枚举；或 WebSearch `site:seller-us.tiktok.com/university/essay`
- 三个陷阱：① 学院首页 `/university/home` 是 CSR 空壳，**不能当发现入口**；② 中文跨境中心 `seller.tiktokshopglobalselling.com` 同样是 CSR 空壳，不可抓且不作来源；③ **WebFetch 失败不等于有登录墙**，必须带 UA 复验一次再下结论

**TikTok 政策的「每日巡视」配方（业内通行做法，2026-10-21 调研）**

TikTok Shop 的 Policy Center 页面本身**带 `NEW` / `UPDATE` 徽章和页面日期**（如「Seller Enforcement Policy · NEW · Published on Oct 6, 2026」），但**没有 changelog、没有 RSS、没有公告 API**。所以业内的做法（如 getlive.ai）就是**每天去看一眼，比对徽章与日期变化**，而不是订阅。

```
1. 打开 seller-us.tiktok.com/university → For Sellers → Policy Center → Latest policies
2. 记录每条政策的：标题 + 徽章(NEW/UPDATE) + 页面日期
3. 与上一日快照 diff，新增/变号的即为当日候选
4. 打开候选页取正文 → 走步骤 4 四维验证
```

- **CSR 限制**：该页是前端渲染，curl / WebFetch 只拿到空壳。须用浏览器渲染（browser 工具）或找到内嵌的 JSON 接口
- **网络限制**：`seller-us.tiktok.com` 与 `newsroom.tiktok.com` 两个子域在本机会话**时通时断**（2026-10-21 实测整体超时，而 `www.tiktok.com` 2.5 秒 200）——巡视失败要先判网络，不要判「无更新」
- **兜底通道**：`ppc.land` 的 RSS 按关键词 `TikTok Shop` 筛（实测近 7 天 1 条），可作当期补充，但**它是 T1 报道不是官方原文**，用它立的卡须在审计注明「T1 报道，官方原文未取到」
- **明确不可行**：TikTok Shop Partner Center API 只开放商品/订单/履约/资金等**店铺数据**（且需开发者资质 + 3 周审核），**没有政策公告接口**；EchoTik / Kalodata / FastMoss / Upscrape 等第三方平台做的全是商品与达人数据，不碰政策文本。**不存在「订阅即得」的 TikTok 政策通道。**

### 步骤 3：廉价预筛 + 定 shortlist

**为什么加这一步**：昂贵环节（抓取 + 四维验证）只跑 shortlist，验证成本与候选数解耦。

#### 3.1 零成本硬淘汰（不消耗任何抓取）

只砍**结构性不合格**，不砍「看起来不重要」：

| 判据 | 代码 | 为什么零成本 |
|---|---|---|
| T3 / 表外域名 | `DISALLOWED_SOURCE` / `SOURCE_NOT_IN_REGISTRY` | 看域名即可 |
| 平台范围外（Temu/eBay/Shein 等平台自身动作） | `PLATFORM_OUT_OF_SCOPE` | 标题点名平台 |
| 重复链接 | `DUPLICATE_URL` | canonical 归一化后比对 |
| 跨期无新进展 | `DUPLICATE_STORY` | 话题指纹命中 topic-registry |
| A1 推广 / A2 打包合集 / A3 纯预告 / A6 无后果人事 / A8 汇率运价日更 / A9 二手解读 | `A1`…`A9` | 标题即可判 |
| 非文章页形态（根路径、`/search/`、`/tag/`、`/category/`） | `NOT_ARTICLE_PAGE` | 看 URL 路径 |

> ⚠️ **预筛阶段不做质量判断。**「这条看着不重要」「这条不像 P0」都不是淘汰理由——跨境标题常不含关键信息（「亚马逊发布重要更新」），靠标题排序会误杀最该收的政策类。预筛只回答一个问题：**它有没有资格被验证。**

#### 3.2 分区归类

按步骤 5.1 的 5 分区口径给每条候选打 `zone`。归不了类的（既不是平台、不是监管、不是物流、不是大盘、也不是社区）判 `LOW_SELLER_RELEVANCE` 淘汰。

#### 3.3 定 shortlist

```
shortlist 目标 38 条：①**8** ②**8** ③**8** ④**8** ⑤6
  ②③④⑤ = 各自上限 × 2（4×2、4×2、4×2、3×2）
  ⚠️ **① 是唯一例外：8 而非 12**。① 上限 6 但只需「三平台各 2-3 条」候选即可覆盖，按上限 ×2 取 12 是浪费验证预算
  ① 区内按平台分组定 shortlist（Amazon 3 / Walmart 3 / TikTok Shop 2），某平台不足则缺口让给候选最多的平台
  某区不足 → 缺口让给候选最多的区，总数不硬凑
  区内排序：只按首发日新→旧，不做质量排序
```

> shortlist 是**验证预算**，不是选稿结果。取 2 倍是因为四维验证实测淘汰率约 30-40%，2 倍才够填满版面（版面上限 21 → shortlist 38，按各区上限分别 ×2）。
> ⚠️ **配额四处联动**：版面（5.5，下限 ①3②3③2④2⑤3=13，上限 ①6②4③4④4⑤3=21）→ 本处 shortlist（①8②8③8④8⑤6=38）→ YAML `early_stop_zone_min`（按 Tier A 各区源数定，①3②3③4④2⑤3=15，**不是** shortlist 的固定百分比）→ `early_stop_candidates`（38）。改任一处必须重算其余三处。v2.10.0 曾因三处各写一套数字，出现「shortlist 标 26、分区加总 22、版面说明算不出 13」的漂移。

### 步骤 4：溯源 + 四维验证（只跑 shortlist）

**输入**：shortlist
**输出**：验证通过的候选（含 `canonical_url` + `verification`）；失败者进 `rejected[]`

#### 4.0 成本阶梯（顺序不可颠倒）

| 阶 | 动作 | 成本 | 覆盖的判据 |
|:--:|---|---|---|
| 1 | 纯字符串判定 | 0 | 域名白名单、URL 形态、转载声明关键词、日期格式、跨期重复 |
| 2 | 抓一次 `canonical_url` 正文 | 1 次抓取 | 维度①～④ 的主判据 + 确认首发日 |
| 3 | WebSearch 补首发 / 补具体文章页 | 才用 | 阶 2 判不了时才做 |

**一条候选最多 3 次抓取**（1 次原文 + 2 次补位）。用完仍定不了 → 淘汰并写代码。

> 三阶的顺序不是「想先做哪个」，是「哪个更便宜先做哪个」。反了就是拿最贵的工具去回答最便宜的问题。

#### 4.1 维度① — 域名一致性

```
提取 source_name → 提取 canonical_url 域名 → 判断是否匹配
✅ 匹配 → 维度②
❌ 不匹配 → 淘汰（代码 SOURCE_DOMAIN_MISMATCH）
```

- ⚠️ **语义级主体校验**：标签与域名不能只「格式同构」，须由 LLM 判发布主体一致。来源标 Marketplace Pulse 但落点在 36kr 二级转载 → 判 `SOURCE_DOMAIN_MISMATCH`（标签主体与链接主体不是同一发布方）
- ⚠️ **官方多域/多语站点须核对页面范围**：同一路径或同一 `knowledge_id` 在不同域名/区域参数下会解析到不同市场。例：TikTok Shop 卖家学习中心须 `seller.tiktokshopglobalselling.com` + `shop_region=us` 才是美国站，`seller.tiktokglobalshop.com` 同 ID 会落到日本站 → 内容与页面适用范围不符。凡官方帮助中心/规则页，须核对「域名 + 区域/locale 参数 + 页面标题与适用范围」三者一致；JS 渲染页 WebFetch 常只取到外壳，用 WebSearch 索引片段交叉确认
- ⚠️ **UGC 平台域的白名单是必要非充分**：`mp.weixin.qq.com` 下任意账号都能通过域级检查（含服务商营销号）。凡落点在此域，必须核实**账号主体**（官方号=T0 / 行业媒体号=T1 / 个人营销号=T2 仅线索），并在审计该行注明「账号主体：XXX，定级：TX，理由：…」；主体无法确认 → 淘汰

#### 4.2 维度② — 具体文章页

```
✅ 具体文章页 → 维度③
❌ 聚合页/列表页/搜索页 → 淘汰（NOT_ARTICLE_PAGE）
```

判定：path 为根路径、页面为文章列表，或为 `/search/` `/tag/` `/category/` `/archive/` `/topic/` `/column/` 目录 → 聚合页。`/blog/<slug>`、`/articles/<slug>` 只要正文是具体文章即通过；目录根（仅 `/blog/`、`/articles/`）淘汰。此外**页面标题/正文出现 `newsroom`、`insights`、`updates` 这类版块词且无单一文章主体**时同样判聚合页（validator 只拦路径与分页模式，这三个词靠人工判定兜底）。

```
❌ gs.amazon.cn/news/summary · cpsc.gov/Recalls · sell.amazon.com/blog/announcements · 任何目录/搜索页
✅ gs.amazon.cn/news/news-notices-260615 · ecomcrew.com/e651-amazon-changes/
```

⚠️ **官方 release notes 类页面**：沃尔玛政策更新集中在 `marketplacelearn.walmart.com/releasenotes`，**条目无独立 URL**。立卡必须落到 `guides/...` 条款页或上游监管/承运商官方页；确实只能引 release notes 时，审计该行必须标注「载体为官方 release notes」。

#### 4.3 维度③ — 内容一致性（7 项硬检查）

1. **主体一致**：平台、监管机构、企业或产品主体一致
2. **地区一致**：美国站、欧洲站、全球范围不得互相扩大
3. **时间一致**：发布日期 / 生效日期 / 截止日期分别记录，不得混淆。`[date_from, date_to]` 是采集与排序依据、**不是淘汰门槛**——窗口外候选若首发日可确认且属今日新发现，可收录，卡片标注实际首发日并在审计注明；已验证的官方 deadline/活动提醒例外保留
4. **数字一致**：金额、比例、数量、日期必须能在原文中定位
5. **实体覆盖一致**：标题与摘要涉及的每个独立实体均须被链接覆盖（N:N）。摘要有「3 款产品」但链接只覆盖 1 款 → 淘汰（`ENTITY_COVERAGE_MISMATCH`）
6. **事实与解读分离**：原文事实写 `summary`，判断与行动建议写 `impact` / `action`
7. **细节可溯源（防串味）**：摘要里每个具体细节（会期与城市、金额、数量、日期）都必须能在**本条 canonical_url 的原文正文**里定位。撰写时极易从其他文章或记忆里串入相邻事实。**来源没有的细节一律删掉，不去补全**（`DETAIL_UNSOURCED`）

```
抓到 canonical_url 正文 → 7 项全过 → 维度④
                        → 任一失败 → 淘汰（CONTENT_MISMATCH + 子项）
```

#### 4.4 维度④ — 首手源追溯

```
IF tier=T2 且报道对象就是社区反应/卖家讨论本身:
   → 保留，source_name 保持社区主体，标「社区观察」；不得把未证实主张写成事实
IF tier=T2 且报道对象不是社区讨论本身:
   → 搜 T0/T1，找到则更新 source_name/tier/canonical_url 并重跑维度①-③；找不到淘汰（NO_PRIMARY_OR_ORIGINAL_SOURCE）
IF tier=T0/T1:
   ✅ 通过
```

- ⚠️ **转载站判据**：即便 tier 是 T0/T1，仍须检查**页面正文本身**是否自带指向他站的原文声明（`[Source]`、`Source:`、「原文链接」、「来源：xxx」、「本文转载自」、「via xxx」）。出现即说明该页是转载/二次发布，发布主体 ≠ 首发主体 → 必须溯回首发域，把 `source_name` / `tier` / `canonical_url` 全改为首发方，卡片日期改**首发日**；找不到可直达的首发页则淘汰
- ⚠️ **标题主体锚定**：卡片标题或摘要出现第三方 T0/T1 主体名（「Marketplace Pulse：…」「海关总署：…」）时，`canonical_url` 必须落在该主体官方域，不得落在转载/聚合页；落不到即淘汰

#### 4.5 裁决

四维全过 → 步骤 5。任一维度失败 → 淘汰并写代码，不回候选池。失败后最多一次换全新 URL 的重试，重新从 4.0 阶 1 开始。

### 步骤 5：定档 + P0 上限 + 配额 + 排序

**输入**：验证通过的候选
**输出**：定稿清单（按分区填满版面）

跨日去重已在步骤 3.1 用零成本判据做过，此处不重复；若发现漏网，按 `DUPLICATE_STORY` 淘汰并回填步骤 3 的缺口。

#### 5.1 执行顺序（不可调换）

```
① 硬淘汰 → ② A 类排除 → ③ B 类降档 → ④ 定档 P0/P1/P2 → ⑤ P0 上限校正 → ⑥ 按分区配额选 → ⑦ 档内排序
```

三条顺序约束：
- **先排除后定档**。反了，好新闻的光环会把噪声带进来
- **先验证后判时效**。跨境常「旧闻新发现」（官方 10-08 发布、中文可获取 10-20），先判时效会误杀政策类
- **先定档后限 P0**。P0 上限是版面构型问题，不是「这条值不值」问题

判据细节与锚定例子见 `references/selection-score.md`（第五节定档、第六节配额、第七节排序）。本节只留执行要点。

#### 5.2 档位

| 档 | 含义 | 版面地位 |
|:--:|------|---------|
| **P0** | 卖家明天必须改做法 | 头条与看点 |
| **P1** | 有明确影响，但不用明天动手 | 正文主体 |
| **P2** | 有信息量的背景与趋势 | 补空位（含 B 类降档） |

定档只回答一个问题：**卖家明天要不要改做法**。不问「这事大不大」「谁发的」「写得多好」。

#### 5.3 关键约束

- **不用分数，用档位**。绝对分会被模型堆在中间档，真实差异被吃掉
- **来源等级（T0/T1）不参与内容层排序**——那是四维验证的职责，不该再算一次
- **P1 = 卖家要动一下**，不是「卖家该知道」：只有数字和口径、读完不知该改什么的（品类集中度、全站 GMV、份额变化）一律 P2
- **P0 带 30 天时间锚点**：生效/截止类判据须落在 30 天内，超窗口降 P1。带处罚后果的规则变更、召回、履约中断**不受此限**
- **P0 上限 = 卡片数 × 40%**（最少 1 条，基数含社区卡）：超限**降档不删卡**，按「受影响卖家数 × 是否需明天动手」排序，降档写 `audit_note: 降档:P0超限→P1`
- **A 类 10 项直接排除，不定档**；**B 类 4 项最高 P2**（清单见 `selection-score.md` §3/§4）
- **社区帖走独立口径**（`可复用性/具体度/对应时点`），不套主档位，审计写 `[社区]`
- **时效以首发日为准**，不用扣分制

#### 5.4 用户画像（仅档内排序参考）

早报主体是通用跨境资讯，画像匹配**不改变档位与配额**；仅在同档同分区内优先选更相关的一条。关键词示例：健康个护、FBA 费用与仓储、广告投放与 ACOS、Prime Day/黑五备货、FDA/CE/FCC 合规——使用时替换为自己类目的关键词即可。

#### 5.5 精选原则

- **版面配额**（下限 / 上限）：

  | 分区 | 下限 | 上限 |
  |:--:|:--:|:--:|
  | ① 平台政策与费用 | 3（三平台各 1） | **6** |
  | ② 合规与监管 | 3 | **4** |
  | ③ 物流与供应链 | 2 | **4** |
  | ④ 行业与市场 | 2 | **4** |
  | ⑤ 卖家社区 | 3 | **3**（固定） |
  | **合计** | **13** | **21** |

  低新闻量日按实际出，不足 7 条在审计说明原因。各区达上限后**不再加条**，多余 P0/P1 按 ② > ① > ③ > ④ 的优先级让位或降档（写 `audit_note: 降档:该区达上限`）。
- **① 区三平台覆盖规则**：Amazon / Walmart / TikTok Shop **各至少 1 条**，该区**上限 6 条**（下限仍 3，三平台各 1 即达标）
  - 区内排序：按平台分组，每组内按档位；平台顺序 Amazon → Walmart → TikTok Shop
  - 单平台超过 3 条时，第 4 条起须为 P0 或带处罚后果的规则变更，否则让位给其他平台
  - **缺口处理（关键）**：某平台当日无**已通过四维验证**的资讯时，**不得用转载、旧闻、服务商解读凑数**，审计该行写 `①区缺口:<平台名>`，用其余两平台的 P0/P1 补到 ①≥3
  - 三平台合计仍不足 3 条 → 按实际数量出，审计注明；**绝不为满足覆盖而降低验证标准**
  - ⚠️ 供给现实：Amazon 侧靠 `gs.amazon.cn`（周更偏日）+ `Amazon Ads`（条目无日期）；Walmart 侧靠 `marketplacelearn.walmart.com`（列表不可解析，多由 T1 媒体转述）；**TikTok Shop 侧仅 `seller-us.tiktok.com`（需已有 knowledge_id，被动触发）**。TikTok 每日 1 条当前供给不具备，缺口留痕即合规
- **不为凑满降低验证标准**；同一来源通常不超过 2 条（重大连续公告例外）
- 知无不言 3 条为配额强制项（按观看数 + 关注数硬选，同热度段内优先运营实操：广告/Listing/库存/合规）；不足 3 条须在审计写明已查渠道与缺口，不得用低质帖凑数
- 知无不言卡片计入精选总数，Header 的「精选 X 条」必须等于全部 `.card` 数量（渲染器自动算）

#### 5.6 主题分区（5 个，顺序固定）

| 序 | 分区名 | class | 典型内容 |
|:--:|---|:--:|---|
| 1 | 🟣 平台政策与费用 | `cat-policy` | 平台方发出的规则/功能/费用：亚马逊规则变更、Buy Box、标题/图片/A+ 规范、账户状况新规、广告产品动态、FBA/AWD/GWD 费用、平台扩张招商。**只关注 Amazon / Walmart / TikTok Shop**（`PLATFORM_OUT_OF_SCOPE`）。费用类在区内聚为「费用」小组 |
| 2 | 🔴 合规与监管 | `cat-reg` | 政府/监管机构口径：CPSC 召回、TIC DV/锂电池验证、CE/FCC/FDA、EPR/PPWR/WEEE、IP 侵权，**以及税务与关务（VAT、关税、报关模式 0110→9810、涉税稽核）** |
| 3 | 🟡 物流与供应链 | `cat-logistics` | 头程/仓储/尾程：海运空运运价、FBA 入仓截止、GWD/AWD 仓、FBM 履约规则、清关时效。**不含税则与申报** |
| 4 | 🟢 行业与市场 | `cat-market` | 大盘数据、平台格局与资本动态：汇率、大卖财报、Marketplace Pulse 数据、品类规模 |
| 5 | 🔵 卖家社区 | `cat-community` | 知无不言精华帖、Reddit 等社区讨论 |

**归类判定（按发布主体裁轴）**：
- 第一刀切发布主体：平台方发 → ①；政府/监管发 → ②。两者重叠以发布主体为准，不看题材
- **税务与关务一律归 ②**（VAT、关税、报关模式、涉税稽核），**不进 ③**
- **平台扩张/招商走 ①**，④ 只收大盘与资本数据
- 知无不言统一归 ⑤；官方公告本身归 ①（「标题 75 字符官方通知」→①，「知无不言讨论帖」→⑤）
- **空分区不省略**：渲染器自动输出「⚪ 今日暂无 X 更新」占位

> 改分区名须三处同步：`validate-report.py:SECTION_NAMES` + 本节 + `references/html-spec.md`，只改一处会让 validator 拦截交付。

### 步骤 6：出稿 + 门禁 + 回写

#### 6.1 填数据，别写 HTML

```
python scripts/render-report.py --example > candidates.json    # 1. 生成骨架
# 2. 填 date / window / scope_note / countdown / trends / timeline / sections / rejected
python scripts/render-report.py candidates.json --audit 早报审计  # 3. 出 HTML + 审计
```

渲染器负责以下部分，**不要人工重做**：
- Header 条数、独立来源数、来源 pill 列表与分级色
- 每个分区 `section-header` 的 `.count`、5 分区顺序与 class、空分区占位
- 卡片 `card-date → card-source → badge` 的 meta 顺序、`fold-impact` / `fold-act` 两段、底部「→ 原文链接」
- KPI 条、倒计时三档、nav-bar 计数
- **审计的定档行**（档位 + 分区符号 + 行数）——`AUDIT_ZONE_MISMATCH` / `P0_RATIO` 结构性不可能出错

**不要手写 HTML，也不要逐条对照 class 名。** `references/html-spec.md` 只是视觉规范，仅在改配色、加组件时查阅。

**渲染器会先做数据自检**（卡片数 ≥7、字段齐全、URL 不重复、卡片日期 ≤ 生成日、P0 ≤ 40%），不过就拒绝渲染——错误在出稿前就挡住。

#### 6.2 门禁

```
python scripts/validate-report.py 跨境早报-YYYY-MM-DD.html [--project-root <项目根>]
```

26 项（23 HTML + 3 审计）全过才可交付；exit≠0 **不得交付**，先定位修正，最多 2 轮修复重验；仍失败则只交审计和失败说明。

> 渲染器保证了结构，validator 这时真正在查的是**内容**：域名白名单、禁止域名、聚合页、重复 URL、日期真实性、来源 pill 与卡片是否对得上。

#### 6.3 审计

顺序强制：**先落审计，再跑门禁**（审计来自候选处理记录，不依赖 HTML 验证结果）。脚本已生成概况 + 定档行 + 淘汰表骨架，人工只补两处：

- `audit_note`：为什么这条是 P0、为什么不是头条（降档原因写在这里）
- `rejected[].reason`：为什么被拦

审计必须能回答「这条为什么没进、被哪条规则拦的」。不允许「其他原因」。

**淘汰记录规范**（`rejected[]` 的代码取值）：

| 代码 | 含义 |
|:---:|---|
| `URL_UNREACHABLE` | 页面无法访问 |
| `NOT_ARTICLE_PAGE` | 列表页/分类页/搜索页/聚合页 |
| `SOURCE_DOMAIN_MISMATCH` | 来源标签与实际发布主体不一致 |
| `NO_PRIMARY_OR_ORIGINAL_SOURCE` | 无法追溯官方或原创来源 |
| `CONTENT_MISMATCH` | 摘要与页面正文不符 |
| `ENTITY_COVERAGE_MISMATCH` | 单链接不能覆盖标题/摘要中的多个实体 |
| `DATE_UNCONFIRMED` | 无法确认真实发布日期 |
| `OUT_OF_DATE_WINDOW` | 首发日无法确认且有反证；窗口外但首发日可确认的旧闻不淘汰 |
| `REGION_SCOPE_MISMATCH` | 地区或站点适用范围被扩大/写错 |
| `DUPLICATE_URL` / `DUPLICATE_STORY` | 链接重复 / 同一事实往期已报且无新进展 |
| `DETAIL_UNSOURCED` | 摘要含原文里找不到的细节 |
| `LOW_SELLER_RELEVANCE` | 与目标卖家群体关系过弱 |
| `DISALLOWED_SOURCE` | T3 或其他禁用来源 |
| `SOURCE_NOT_IN_REGISTRY` | 最终链接域名未在总表登记（白名单外，validator 同名校验） |
| `PLATFORM_OUT_OF_SCOPE` | 平台范围外：Temu/eBay/Shein 等平台自身动作（只收 Amazon/Walmart/TikTok Shop） |
| `EVIDENCE_UNREADABLE` | 正文残缺到认不出「谁、何时、改变了什么」（只有标题、只剩导航、抓回 403 页） |
| `TITLE_BODY_MISMATCH` | 标题与正文核心不符，以正文为准不得入选 |
| `SPECULATION` | 只有传闻、预测、内部消息，无可核验的已发生事实 |

> A 类排除（A1–A10）与 B 类降档（B1–B4）是**选稿阶段**的处置，不进 `rejected[]` 的代码表，清单见 `references/selection-score.md` §3 / §4，审计按 `淘汰:A3` 这类格式记。

#### 6.4 交付与回写

1. 展示 HTML 文件；若是自动化调度触发，更新执行记录
2. **回写 `早报状态/topic-registry.md`**（与审计同级强制）
   - 新采用话题 → 登记（指纹 / 首报日=今日 / canonical_url / deadline / 状态=监控中）
   - 已存在的延续话题 → 「最后确认」刷今日
   - deadline 已过且无后续节点 → 移入已归档（**单节点过后即归档**；有后续节点的拆双节点跟踪，全部节点过了才归档）
   - deadline 在未来 45 天内 → 刷新「三、倒计时看板」
3. **回写 `早报状态/channel-health.md`**：新故障 → 更新该行（`last_verified` + fallback）；访问正常 → 只刷「最后确认」
4. **状态文件瘦身**：`python scripts/compact-state.py <项目根> --apply`（默认 dry-run，写盘前备份到 `.backup/`）
   - 僵尸话题归档 / 活跃区超长备注外置 `话题详情.md` / 渠道日志外置 `渠道更新日志.md` + 渠道详情
   - **为什么必须做**：实测 数百 KB 状态文件里 130/206 行是僵尸话题，不治理则每期读入的上下文持续膨胀，且过期话题污染预筛
5. **刷新期次索引页**：`python scripts/build-index.py <项目根>`
6. 向用户简报：只出现「精选 X 条 / 采用 Y 个来源 / 本条来自 XXX」这类人话，不出现工具名、步骤号、HTTP 状态码

## 🚫 不要做（Anti-patterns）

### 采集阶段
- ❌ 不要在验证通过前就开始写卡片摘要
- ❌ 不要因为某条目"看起来重磅"就跳过验证
- ❌ 不要为了凑数放水通过不合格条目
- ❌ 不要手动猜测/编造摘要内容
- ❌ 不要把多个渠道的"不可达"标注为"已用"

### 验证阶段
- ❌ 不要把"域名看起来差不多"当作通过
- ❌ 不要对单条链接却覆盖多实体的摘要放行
- ❌ 不要在验证失败后无新URL就重新回到候选池
- ❌ 不要把普通 T2 线索直接当作事实来源；报道对象为社区讨论本身时，按步骤4.4 的社区观察例外处理
- ❌ 不要将社区观点写成已证实的事实

### HTML 生成
- ❌ 不要使用聚合页/列表页 URL 作为卡片链接
- ❌ 不要在日期字段使用模糊时间
- ❌ 不要跳过后生成自动检查
- ❌ 不要在摘要中编造原文没有的数据

### 交付
- ❌ 不要向用户暴露采集细节
- ❌ 不要在淘汰记录中写"其他原因"
- ❌ 不要合并不同来源的资讯而不保留各自 URL

### 数据源使用
- ❌ 不要使用 T3 禁用来源标记为"来源"
- ❌ 不要引用未登记总表的来源作为最终链接（validator 第 3 项会拦截）；发现表外高价值源必须先登记再使用
- ❌ 不要把聚合/UGC 平台（大数跨境 10100.com、出海网 chwang.com，T3 禁用）的页面作为来源或线索
- ❌ 不要让 jintiankansha 的URL出现在最终卡片中
- ❌ 不要把 AMZ123 标注为"来源"
- ❌ 不要从转载站"脑补"一手源标签
- ❌ 不要在卡片标题写第三方主体名（如「Marketplace Pulse：…」）却把链接落在转载/聚合平台

## ⏰ 时间格式转换规则

（规则不变，保留原有内容）

卡片中的日期字段必须遵守以下转换规则：

### 标准文章日期
| 原始数据 | 卡片展示 | 示例 |
|---------|---------|------|
| 文章页发布时间 | `YYYY-MM-DD` | `2026-07-02` |

**规则**：所有标准文章卡片统一使用 `YYYY-MM-DD` 格式。不允许"刚刚"、"今日"、"昨天"等模糊相对时间。`[date_from, date_to]` 是采集与排序依据，不是淘汰门槛：窗口外候选若首发日可确认且属今日新发现，可收录，卡片显示**实际首发日**并在审计注明；已验证的官方生效/截止日期或活动提醒例外保留，审计写明事件日期、官方来源和例外理由。

### 即将生效/截止日期
| 场景 | 日期字段 | 附加徽章 |
|------|---------|---------|
| 合规公告（7/8生效） | 公告发布日期（如`2026-05-12`） | 红色徽章 "即将生效" |

**规则**：日期字段本身必须使用文章的实际发布日期，时效性信息通过徽章展示。

### 卡片摘要中的相对时间
| 时效区间 | 标注方式 |
|---------|---------|
| 1-2天 | `2026-07-03（昨日）` |
| 3-7天 | 先按 `[date_from, date_to]` 判断排序权重；超出窗口但首发日可确认且属今日新发现，仍可作普通新闻收录，标注实际首发日 |
| 超过7天 | 窗口外旧闻新发现仅当首发日可确认且属今日新发现方可收录（标注实际首发日、审计注明）；首发日无法确认则淘汰（代码 `OUT_OF_DATE_WINDOW`）。已验证的官方 deadline/活动提醒例外保留 |

### Deadline倒计时
```
内部计算: 目标日期 - 当前日期 = 剩余天数
→ 摘要末尾标注: "距离生效仅剩X天"
```

**倒计时必须基于当前真实日期动态计算，不能写死。**
